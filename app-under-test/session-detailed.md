# Подробный лог сессии: доска объявлений «Свои люди»

## 1. Исходный запрос

Нужна была идея приложения с оплатой (по типу Ozon) или приложение, заменяющее рутину — предложено 10 вариантов, из которых выбраны идеи №3 (аренда/услуги между соседями) и №7 (биржа микрозадач). На их основе сформулировано финальное ТЗ:

Приложение для жильцов дома. Жильцы (исполнители) размещают объявления об услугах с описанием и ценой («приготовлю борщ за 1000 ₽», «уберусь в квартире за 5000 ₽»). Другие жильцы бронируют объявление и связываются с автором по телефону. Чат — под вопросом. Оплата/предоплата — под вопросом.

### Обсуждённые до разработки вопросы

**Чат.** Простой чат (без реального времени) добавил бы ~10–15% к объёму работы, полноценный (реальное время, уведомления) — ~20–25%. Рекомендация: не делать чат в первой версии, раз уже есть телефон как канал связи. Принято: чата нет.

**Предоплата.** Если платформа сама держит деньги (эскроу) — это фактически финансовое посредничество со своей регуляторной и юридической нагрузкой (возвраты, споры, налоговый учёт), независимо от масштаба проекта. Разовая оплата без удержания — ~15–20% времени, эскроу с холдом и спорами — ~35–40%+. Рекомендация: оплата офлайн, между соседями напрямую. Принято.

**Формат.** Веб-приложение с реальной базой данных (не одноразовое демо) — чтобы данные сохранялись между сессиями и были видны разным людям.

## 2. Архитектурное решение

Реализовано как публикуемый **Artifact** на claude.ai с капабилити `artifact` (`window.claude.use('artifact')`), которая позволяет странице сохранять новую версию себя самой (`publish(html)`) — это и есть «база данных» в данном случае: HTML-страница хранит своё состояние (пользователи, объявления) в виде JSON и при каждом изменении публикует новую полную версию документа. Каждый, кто открывает ссылку, видит актуальную версию.

## 3. Реализованный функционал

- Доска объявлений с категориями: еда, уборка, ремонт, транспорт/дела, питомцы, другое.
- Поиск по объявлениям, фильтр по категориям.
- Регистрация/вход: уникальный логин на латинице (3–20 символов), пароль (хешируется через SHA-256 с солью на клиенте — не настоящая крипто-защита, но защита от случайного/неопытного вмешательства, см. раздел про безопасность ниже), имя для отображения, квартира (необязательно), телефон.
- Размещение объявления: заголовок, категория, цена, описание — данные автора (имя/кв./телефон) подставляются из профиля автоматически.
- Бронирование: подтверждение брони соседом → открывается номер телефона автора, кнопки «Позвонить» (`tel:`-ссылка) и «Скопировать номер».
- Права: удалить объявление может только автор; отменить бронь — автор или тот, кто забронировал (по логину из сессии, а не по свободному тексту).
- Никакой оплаты внутри приложения — итоговая фраза на доске: «Оплата и договорённости — напрямую между соседями, при встрече».
- Чат отсутствует по решению на этапе планирования.

## 4. Хронология проблем и их причины

### 4.1. Ограничение на удаление чужих объявлений
Запрос: не давать удалять объявление, если не ты его создал. Обсуждены варианты (привязка к браузеру / кодовое слово / оба сразу) — пользователь предпочёл полноценную авторизацию. Решение: логин+пароль вместо анонимных полей «имя автора», owner-check по `authorUsername` при удалении, по `bookedBy.username` или `authorUsername` — при отмене брони. Отдельно оговорено: раз вся страница статична и данные (включая хеши паролей) физически лежат в её собственном коде — это защита уровня «обычный сосед не тронет чужое через интерфейс», не крипто-защита от специалиста с доступом к консоли браузера.

### 4.2. Баг №1 — пропали все стили и «только просмотр» показывалось даже владельцу
**Причина:** инструмент публикации Artifact сам оборачивает переданный файл в `<!doctype html><html><head>…</head><body>` при первой публикации. В коде по ошибке эти теги были продублированы внутри самого файла. Из-за вложенной/сломанной структуры документа браузер терял часть содержимого головы страницы (стили), а API `window.claude` инициализировалось некорректно — отсюда и ложное «только просмотр» даже для владельца артефакта.
**Исправление:** убраны лишние `<!doctype>/<html>/<head>/<body>` теги из файла, который передаётся именно в инструмент публикации Artifact.

### 4.3. Конфликты версий при повторной публикации
При попытках переопубликовать исправленный файл инструмент несколько раз отказывал с ошибкой: «новая версия сохранена изнутри страницы (кем-то), а прочитать её для слияния нельзя — в этом окружении заблокирован сетевой доступ к хосту артефактов (`*.frame.claudeusercontent.com`)». Это происходило из-за собственных действий внутри страницы (в т.ч. регистрации самого пользователя), которые платформа воспринимает как новую версию. Слияние версий вручную было невозможно из-за сетевого ограничения текущей рабочей среды. Каждый раз использовалась принудительная перезапись (`force`) — **только после явного согласия пользователя**, поскольку это стирает то, что было сохранено «изнутри» (в частности, один раз так был потерян тестовый аккаунт пользователя — с её согласия, аккаунт был тестовый).

Из-за нестабильности версии артефакта дважды пересоздавался «с нуля» по новому адресу (новый `file_path` → новый URL), чтобы получить чистую историю версий без накопленных конфликтов.

### 4.4. Попытки автотестирования через браузер и их ограничения
При тестировании через встроенную автоматизацию браузера (клики по вкладке «Регистрация» внутри iframe артефакта) многократно происходило зависание захвата скриншота (таймаут 30 секунд у `Page.captureScreenshot`), при этом дерево доступности страницы продолжало отвечать — то есть сама вкладка не была полностью заморожена. Это выглядит как проблема самого инструмента автоматизации при работе с вложенным cross-origin iframe артефакта, а не обязательно баг в самом приложении: клик по вкладке переключения формы не вызывает никакого сохранения на сервер (`save()`/`publish()` в этом обработчике не участвуют), и после зависаний свежая перезагрized страницы каждый раз показывала корректно сохранённое состояние без потери данных. Тем не менее до конца «глазами» через автоматизацию пройти полный цикл регистрации не получилось — это осталось на ручную проверку пользователем.

### 4.5. Баг №2 — стили пропадали через секунду после регистрации/брони (в реальном браузере пользователя, не в тестовом)
Пользователь сообщила: при открытии страницы после регистрации стили сначала подгружаются, а через секунду полностью сбрасываются.
**Причина:** при пересборке полной HTML-страницы для повторной публикации (`buildFullHtml()`, вызывается при каждом сохранении — регистрация, новое объявление, бронь и т.д.) код брал содержимое `<head>` не из заранее известного шаблона, а «подсматривал» его из текущей живой страницы в браузере (`document.head.outerHTML`). В момент публикации `<head>` мог уже содержать посторонние технические элементы, добавленные самой платформой поверх исходного кода — и они «замораживались» в новую версию страницы, из-за чего при следующей загрузке эта версия оказывалась структурно испорченной, а стили исчезали не сразу, а после перерисовки/перезагрузки.
**Исправление:** содержимое `<head>` (мета-теги, шрифты, весь CSS) теперь зашито в код как неизменная строковая константа (`HEAD_HTML`), а не считывается с живой страницы в момент публикации. Это устраняет саму возможность попадания посторонних элементов в сохраняемую версию.

### 4.6. Убраны по запросу: read-only-режим и его сообщения
Полностью удалены: баннер «эта копия доски открыта только для просмотра», текст «попросите владельца доски дать доступ на редактирование», отключение полей формы регистрации/добавления объявления в этом режиме, переменная `readOnly` и вся связанная с ней логика. Теперь приложение просто всегда пытается сохранить изменения через `claude.use('artifact')`; при неудаче — обычное сообщение об ошибке без деградации функционала.

## 5. Финальные артефакты

1. **Общая доска (публичная ссылка, данные видны всем, у кого есть доступ):**
   https://claude.ai/code/artifact/34010453-d307-4256-b8ee-673f14f7e1da
   Чтобы соседи могли не только смотреть, но и писать (регистрироваться, размещать, бронировать) — им нужно выдать права на редактирование через меню «Share» у артефакта, иначе они попадут в режим без прав на запись (сообщение об этом теперь не показывается — тихо просто не будет сохраняться).

2. **Локальный файл `index.html`** — самостоятельная копия того же приложения, которую можно открыть двойным кликом из любой папки без интернет-платформы Claude. Отличие: поскольку вне платформы `window.claude` недоступен, добавлен запасной механизм хранения — все данные (аккаунты, объявления, брони) сохраняются в `localStorage` браузера, в котором открыт файл. Это значит: всё работает полностью в рамках одного браузера на одном устройстве, но не синхронизируется между разными людьми/устройствами — для совместного использования нужна именно ссылка на доску, а не локальный файл.

## 6. Что осталось непроверенным / на что обратить внимание

- Полный цикл «регистрация → размещение объявления → бронь → просмотр телефона» на общей ссылке не был до конца пройден автоматизированным тестом (см. п. 4.4) — стоит проверить вручную ещё раз, особенно после свежего фикса из п. 4.5.
- Права на редактирование для соседей нужно выдавать вручную через «Share» — это не настраивается из кода.
- Хеширование пароля с солью через `crypto.subtle` — базовая защита от случайного доступа, не полноценная безопасность (см. п. 4.1).
