# Итоговый отчёт: QA приложения «Свои люди»

Честный отчёт по каждому пункту задания — без приукрашивания, с прямыми
ссылками на файлы и коммиты, по которым можно проверить каждое
утверждение самостоятельно.

---

## 1. Работающий результат

Что протестировано: приложение «Свои люди» (`app-under-test/index-local.html`)
по четырём разделам [`qa-spec.md`](qa-spec.md) — функциональность
(регистрация, вход, размещение объявлений, бронирование, права по
логину), доступность (клавиатурная навигация, фокус в модалках, `Escape`,
`axe-core`), устойчивость к кривым/чужим данным (инъекции, обход
валидации, подделка сессии, гонки записи), нагрузка/объём (50–500
записей, квота `localStorage`, отклик поиска).

Как запустить и убедиться самостоятельно:

```bash
npm install
npx playwright install chromium
npm test
```

Ожидаемый результат: **9 passed / 13 failed**, стабильно при повторных
прогонах (проверено многократно на протяжении всей работы, в т.ч. прямо
перед написанием этого отчёта). Это не брак — 13 падений это честные
ассерты на реальных, задокументированных дефектах приложения (см. раздел
4 «Честно» ниже и [`qa-spec.md`](qa-spec.md) за деталями каждого
сценария). HTML-отчёт прогона: `npm run test:report`.

Автотесты лежат в [`tests/`](tests/): `accessibility.spec.js`,
`keyboard-focus.spec.js`, `functional-flow.spec.js`, `permissions.spec.js`,
`security.spec.js`, `volume-bugs.spec.js` — 22 теста, все идут через
реальный UI (клики, заполнение полей), а не через вызовы внутренних
функций страницы в обход интерфейса (исключение — генерация объёма
данных в `volume-bugs.spec.js`, это осознанно, см. комментарий в файле).

## 2. Агенты

Работа велась в трёх разных режимах — намеренно, чтобы сравнить подходы,
а не потому что один режим не справился:

- **Параллельно** — [`qa-report.md`](qa-report.md). Три независимых
  субагента одновременно, каждый в своей зоне без пересечений
  (функциональность / доступность / устойчивость к данным). Wall-clock
  ~11 мин 15 с, суммарно 290 497 токенов на троих, 330 вызовов
  инструментов.
- **Последовательно** — [`qa-report-solo.md`](qa-report-solo.md). Та же
  задача, один поток, без субагентов. ~16 мин 21 с (на 45% дольше), но
  ~84 800 токенов (в 3,4 раза меньше — каждый параллельный субагент
  заново читает файлы и поднимает окружение, последовательный прогон
  делает это один раз). Результаты по существу совпали с параллельным
  прогоном — расхождение только в затратах, не в находках.
- **Независимый ревьюер — дважды, по одному и тому же принципу**
  («агент без памяти о том, как писались тесты/код, перепроверяет с
  чистого листа»):
  1. [`qa-review-independent.md`](qa-review-independent.md) — разовый
     аудит поверх всей существовавшей на тот момент QA-работы (спеки,
     трёх отчётов, кода трёх HTML-вариантов приложения). Нашёл
     критичный необнаруженный дефект (крэш `index-seeded.html`/
     `index-for-artifact-publish.html` вне платформы Claude) и то, что
     один тест маскировал известный баг вместо честного падения. Под
     каждой находкой в файле отмечено, каким коммитом она закрыта.
  2. Тот же принцип, но встроенный в процесс на постоянной основе —
     шаг 4 воркфлоу [`.claude/skills/qa-release-check/`](.claude/skills/qa-release-check/)
     (см. раздел 3). Отдельный `Agent` (`general-purpose`), стартующий с
     чистого контекста, вызывается на каждом прогоне и обязан сам
     записать файл результата — это не разовая проверка, а встроенная в
     повторяемый процесс независимая сверка.

## 3. Workflow

[`.claude/skills/qa-release-check/SKILL.md`](.claude/skills/qa-release-check/SKILL.md)
— повторяемая процедура «QA-прогон перед релизом», вызывается перед
каждым изменением `app-under-test/` (не разовый скрипт). Пять шагов,
каждый оставляет файл-доказательство в `qa-runs/<дата-время>/`:

1. Диф `app-under-test/` с последнего коммита → `01-diff.md`.
2. Сопоставление дифа с затронутыми пунктами `qa-spec.md` → `02-spec-impact.md`.
3. `npx playwright test` → `03-test-run.md`.
4. Независимая проверка покрытия и «маскировки» багов свежим подагентом
   без памяти о том, как писались тесты (см. раздел 2) → `04-independent-review.md`,
   пишет сам агент, исходная сессия не редактирует его содержимое.
5. Итоговый честный отчёт (что прогнали / что упало / что нового / что
   не покрыто / что не успели) → `05-final-report.md`.

Запуск: `/qa-release-check` или фразой «прогони QA-check перед релизом».

**Честно про его текущее состояние:** скилл создан в этой же серии
сессий и ни разу не был вызван автоматически через `Skill()` — список
скиллов Claude Code перечитывается только при старте новой сессии. Всё
описанное выше проверено **вручную**, шаг за шагом по тексту скилла
(результат — `qa-runs/2026-08-27_01-34-26/`, локально, не в git,
директория в `.gitignore` как регенерируемые артефакты). Реальный вызов
по имени/фразе ещё предстоит подтвердить в следующей сессии.

## 4. Честно: что не сработало и не сделано

- **Баг Ф-1** (модалка деталей закрывается сама сразу после клика
  «Забронировать», вместо того чтобы остаться открытой с раскрытым
  телефоном) — **не исправлен в коде приложения**. Тест
  (`tests/functional-flow.spec.js`) честно падает на нём — изначально
  тест маскировал этот баг (переоткрывал модалку в обход), это само
  было находкой независимого ревью и исправлено, но сам баг в коде
  приложения остался.
- **Отсутствие debounce на поиске** (каждое нажатие клавиши — 130–290 мс
  на 350–500 записях, полная пересборка `innerHTML`) — **не исправлено**.
  Задокументировано в [`qa-report-volume.md`](qa-report-volume.md), тест
  `tests/volume-bugs.spec.js` честно падает.
- **Потеря данных при переполнении `localStorage`** (`saveLocalState()`
  проглатывает `QuotaExceededError` в пустой `catch{}`, `save()` всё
  равно показывает тост об успехе) — **не исправлено**. Тот же файл
  `qa-report-volume.md`, тест на это тоже честно падает.
- Доступность (4 нарушения `axe-core` critical/serious, `Escape` не
  закрывает модалки, нет фокус-трапа, нет `role="dialog"`, карточки
  объявлений недоступны с клавиатуры) — **не исправлена**, только
  зафиксирована тестами.
- **Разделы 3.4 (обход валидации цены), 3.9 (самобронирование в обход
  UI), 3.10 (гонка двойного бронирования) `qa-spec.md` — без единого
  автотеста.** Это подтверждено дважды независимо: в
  `qa-review-independent.md` и повторно, с расширенным списком, в
  `qa-runs/2026-08-27_01-34-26/04-independent-review.md` — второй прогон
  independent-review показал, что реальный пробел по покрытию спецификации
  автотестами заметно шире изначально зафиксированного: помимо 3.4/3.9/3.10
  без тестов остаются 3.1–3.3, 3.5–3.7, 3.12 (весь раздел 3, кроме 3.11 и
  3.13), большая часть 1.1–1.4, часть 2.1–2.4 и половина раздела 4.
  Это не сделано и не планировалось в рамках выполненных сессий —
  называю прямо, а не молчу об этом.
- `index-seeded.html`/`index-for-artifact-publish.html` получили технический
  фикс (перестали падать вне платформы Claude), но по-прежнему нигде не
  помечены как «снимок, разойдётся с живым артефактом» — риск повторной
  путаницы («у меня не запускается» из `sessions/session-7.md`) снижен,
  не устранён полностью.

**Прогон тестов сейчас: 9 passed / 13 failed.** Все 13 падений — из
списка выше и ниже, ни одного «непонятного» или флакового падения нет
(проверялось многократно, включая независимую проверку в разделе 2).

## 5. Открытый вопрос к продукту — закрыт

**Видимость телефона третьим лицам** ([`qa-spec.md`, п. 1.4.5](qa-spec.md)):
после чужой брони номер телефона автора и кнопки связи видны **любому**
авторизованному пользователю, открывшему объявление — не только автору и
тому, кто забронировал (`renderDetail()` не проверяет `isAuthor`/`isBooker`
для самого блока `phone-reveal`, только для кнопки «Отменить бронь»
внутри него). Изначально зафиксировано как открытый вопрос в
`qa-report.md`/`qa-report-solo.md`, формализовано пунктом 1.4.5 в
`qa-spec.md`.

**Решение принято: оставить как есть.** Это не баг, а сознательно
принятый компромисс для контекста приложения (закрытый круг соседей по
одному дому, где номер телефона и так не является секретом внутри этого
круга) — не блокер, изменений в коде/тестах по этому пункту не
требуется. Автотеста на это поведение по-прежнему нет (см. раздел 4 —
1.4.5 в списке непокрытых пунктов); при желании зафиксировать решение
регресс-тестом стоит сделать это по тому же принципу, что уже применён
для пункта 3.13 (`tests/security.spec.js`) — зелёный тест, документирующий
осознанно принятое поведение, а не растущий как красный сигнал о баге.
