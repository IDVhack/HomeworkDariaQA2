# Отчёт по тестированию на объёме: «Свои люди»

Проверка раздела 4 спецификации ([qa-spec.md](qa-spec.md)) — поведение приложения на программно сгенерированном большом состоянии, подставленном напрямую в `localStorage['sl_state']` (эквивалент `#app-state` при отсутствии artifact-капабилити, см. `loadLocalState()` в коде). Тестирование выполнено вживую в браузере на `http://localhost:8934/index-local.html`.

## Сгенерированные данные

- **60 пользователей** (`user0`…`user59`) со случайными `displayName`/`phone`/`apt`.
- **Объявления: сначала 350, затем расширено до 500** — вперемешку `open`/`booked` (не сгруппированы заранее), часть записей с намеренно одинаковым `createdAt` (34 дубликата в итоговом наборе) для проверки устойчивости сортировки.

---

## 1. Отклик поиска и рендера списка (4.3–4.5)

| Действие | Размер списка | Время |
|---|---|---|
| Клик по чипу категории (полный `render()`, 350→59 записей) | 350 | **10,4 мс** |
| Клик по чипу категории (полный `render()`, 500 записей) | 500 | **13,5 мс** |
| Загрузка страницы (`domContentLoadedEventEnd`) | 500 | **89,9 мс** |
| **Одно нажатие клавиши в поиске** (`input`-событие → `render()` + `focus()` + `setSelectionRange()`) | 350 | **130–290 мс** (растёт к концу ввода) |
| Одно нажатие клавиши в поиске | 500 | **234 мс** |

**Вывод:** рендер списка и фильтрация по категории масштабируются нормально (10–14 мс даже на 500 записях — не деградирует заметно). **Но поиск как таковой — это реальная проблема производительности**: каждое нажатие клавиши в поле поиска стоит на порядок дороже (130–290 мс), чем клик по чипу, хотя оба пути вызывают один и тот же `render()`. Причина — в обработчике `input` для `#search` (`render()` полностью пересобирает `innerHTML`, затем ищет новый `#search` в свежепостроенном DOM, вызывает на нём `.focus()` и `.setSelectionRange()`, что форсирует дополнительный синхронный layout/reflow браузера). Debounce на вводе отсутствует — при 350–500 записях это уже создаёт заметное «залипание» ввода при быстрой печати.

## 2. Квота `localStorage` (4.6–4.8)

**Уточнение к спецификации:** фактический лимит `localStorage` в тестовом окружении (Chromium) оказался около **~50–52 МБ на origin**, а не «типичных 5–10 МБ», которые изначально предполагались в тексте спецификации (формулировка там исправлена).

Ход эксперимента: origin был заполнен служебными данными почти вплотную к фактическому пределу (оставлено буквально несколько сотен байт свободного места), после чего через настоящую форму «+ Разместить объявление» было создано новое объявление.

**Результат — подтверждённый дефект:**
- `localStorage.setItem('sl_state', ...)` внутри `saveLocalState()` реально бросил `QuotaExceededError` — состояние в `localStorage` осталось **байт-в-байт неизменным** (`stateActuallyChanged: false`, длина строки та же, счётчик объявлений тот же).
- Но код `saveLocalState()` оборачивает `setItem` в `try{}catch(e){}` **без какой-либо обработки ошибки** — исключение молча проглатывается.
- `save()` в ветке без artifact-капабилити после этого всё равно безусловно вызывает `render()` (используя in-memory `state`, который уже обновлён) и показывает `opts.toast` — тост **«Объявление размещено»** появился (`toastVisible: true`), хотя объявление физически не сохранилось.
- В памяти (DOM) новое объявление отобразилось (524-я/524-я карточка), создавая у пользователя полное ощущение успеха.
- **После перезагрузки страницы (4.8)** объявление пропало: счётчик вернулся к прежнему значению, текст «TRUE OVERFLOW» в DOM отсутствует. Данные потеряны безвозвратно, без единого предупреждения пользователю.

**Итог:** сценарий из спецификации подтверждён напрямую и это реальный, воспроизводимый дефект (не гипотетический) — **тост лжёт об успехе при превышении квоты `localStorage`; честной ошибки пользователю не показывается, а созданные данные тихо теряются при следующей перезагрузке.**

## 3. Сортировка «забронировано вниз» на большом списке (4.9–4.10)

Проверено на 523 записях (406 `open` + 117 `booked`, вперемешку, 34 дубликата `createdAt`):

- **Группировка по статусу:** все 406 `open`-записей строго идут раньше всех 117 `booked`-записей (`firstBookedIdx === 406 === openCount`, нарушений границы — 0).
- **Порядок внутри групп по `createdAt` (убывание):** 0 нарушений как в группе `open`, так и в группе `booked` — сортировка `localeCompare` по ISO-строкам дат работает корректно даже при 34 полностью совпадающих значениях `createdAt` (стабильность сортировки не нарушена).

**Итог:** сортировка полностью корректна на объёме 200–500+ записей, дефектов не найдено.

## Сводный итог раздела «Нагрузка»

| Проверка | Результат |
|---|---|
| Рендер списка / фильтр по категории | OK, не деградирует (10–14 мс на 350–500 записях) |
| **Поиск (посимвольный ввод)** | **Дефект производительности**: 130–290 мс на каждое нажатие клавиши, без debounce |
| Квота `localStorage` при превышении | **Подтверждённый дефект**: тост показывает успех, данные тихо теряются, честной ошибки нет |
| Сортировка «забронировано вниз» | OK, 0 нарушений на 523 записях с дублирующимися датами |

Два реальных, воспроизводимых дефекта, оба не связаны с случайностью тестового окружения: отсутствие debounce на поиске и молчаливая потеря данных при переполнении `localStorage`. Оба стоит зафиксировать в бэклоге — особенно потерю данных с ложным тостом, так как это вводит пользователя в заблуждение относительно того, сохранилось ли объявление/бронь.
