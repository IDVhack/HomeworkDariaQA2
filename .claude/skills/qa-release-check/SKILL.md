# QA-прогон перед релизом

Повторяемый воркфлоу для `app-under-test/` (проект «Свои люди»). Задача —
не разовая проверка, а процедура, которую можно честно прогонять перед
каждым изменением приложения. Каждый шаг обязан оставить файл-доказательство
того, что он выполнен, а не просто вывод в чат.

Все артефакты одного прогона складываются в новую директорию
`qa-runs/<YYYY-MM-DD_HH-MM-SS>/` (локальное время). Не переиспользуй
директорию другого прогона. Эта папка — регенерируемые артефакты прогона
(как `test-results/`/`playwright-report/`), не путать с
`qa-review-independent.md` в корне — тот файл про один конкретный
исторический аудит, этот скилл про текущий прогон перед конкретным
изменением.

## Шаг 0 — подготовка

```bash
mkdir -p "qa-runs/$(date +%Y-%m-%d_%H-%M-%S)"
```

Зафиксируй путь `RUN_DIR` — он понадобится на каждом следующем шаге.
Дальше все относительные пути — внутри `RUN_DIR`.

## Шаг 1 — что изменилось в app-under-test/ с последнего коммита

Сначала проверь, есть ли незакоммиченные изменения:

```bash
git status --short -- app-under-test/
git diff --stat -- app-under-test/
```

- Если есть незакоммиченные изменения — диффь `git diff -- app-under-test/`
  (рабочее дерево против HEAD).
- Если незакоммиченных изменений нет (изменение уже закоммичено, QA гоняется
  перед пушем) — найди последний коммит, тронувший `app-under-test/`, и
  сравни его с родителем: `git log -1 --format=%H -- app-under-test/`, затем
  `git diff <hash>^ <hash> -- app-under-test/`.
- Если `app-under-test/` вообще не менялся с последнего прогона (сверься с
  предыдущим `qa-runs/*/01-diff.md`, если он есть) — это тоже валидный
  результат шага, не ошибка: зафиксируй «изменений нет» явно, не пропускай
  файл.

Сохрани полный diff (не только `--stat`) и явный список изменённых файлов в
**`01-diff.md`**.

## Шаг 2 — какие разделы qa-spec.md это затрагивает

Прочитай `qa-spec.md` и для каждого изменённого куска кода (по diff из шага 1)
определи, какие пронумерованные пункты спецификации (`1.x`, `2.x`, `3.x`,
`4.x`) теперь потенциально затронуты — по функциям/DOM-узлам/поведению,
которые правка задевает, а не только по совпадению ключевых слов.

Для каждого затронутого пункта explicit укажи:
- номер пункта и одну строку из qa-spec.md, почему он затронут;
- есть ли на него автотест (в каком файле `tests/*.spec.js` и на какой
  строке) или он покрыт только вручную/не покрыт вовсе.

Если diff пуст (см. шаг 1) — так и напиши: «затронутых пунктов нет, diff
пуст», не изобретай затронутые разделы.

Сохрани в **`02-spec-impact.md`**.

## Шаг 3 — прогон npm test

```bash
npx playwright test --reporter=list
```

Сохрани полный вывод (stdout+stderr, passed/failed по каждому тесту) в
**`03-test-run.md`** — оберни в code fence, добавь сверху одну строку-сводку
(«N passed / M failed») и дату/время прогона.

## Шаг 4 — независимая проверка покрытия (обязательно другим агентом)

Это ключевое требование воркфлоу: шаг 4 обязан выполнять **свежий
подагент без памяти о том, как писались тесты** — не эта же сессия, не тот
агент, что правил код/тесты на шагах 1–3. Используй инструмент `Agent`
(`subagent_type: general-purpose`, `run_in_background: false`, т.к. шаг 5
зависит от результата) с полностью самодостаточным промптом — без ссылок на
«как мы обсуждали» или «как я только что сделал».

Промпт агенту должен:
1. Указать прочитать `RUN_DIR/01-diff.md`, `RUN_DIR/02-spec-impact.md`,
   `RUN_DIR/03-test-run.md`, `qa-spec.md`, и все файлы `tests/*.spec.js`.
2. Явно попросить независимо (не доверяя выводам шага 2) перепроверить:
   действительно ли текущий набор тестов покрывает то, что реально
   изменилось в diff'е — а не то, что менялось в какой-то прошлый раз;
   есть ли изменённое поведение без единого теста на него.
3. Явно попросить проверить каждый тест, который **упал**, и каждый,
   который **прошёл**, по одному и тому же критерию, что уже применялся в
   `qa-review-independent.md`: не «замаскирован» ли тест под известный баг —
   т.е. не обходит ли тест дефект (переоткрытие модалки, catch без
   assert, слишком мягкий/произвольно ослабленный ассерт, `test.skip`,
   заведомо недостижимая ветка) вместо того, чтобы упасть на нём или честно
   зафиксировать его как принятое ограничение (как это сделано для 3.13).
4. Попросить формат ответа: список находок с severity (как в
   `qa-review-independent.md`) + отдельно — список пунктов из
   `02-spec-impact.md`, которые остались без теста.
5. Явно попросить агента написать результат в файл
   `RUN_DIR/04-independent-review.md` самостоятельно (агент должен иметь
   доступ к Write) — не полагайся на то, что примешь его ответ и перепишешь
   сама: пусть он сам создаст файл, это и есть доказательство, что проверка
   прошла независимо, а не была переформулирована исходной сессией.

После получения результата — не редактируй содержательную часть
`04-independent-review.md` от лица подагента (это сломает независимость
доказательства). Если хочешь прокомментировать несогласие — делай это в
`05-final-report.md`, отдельно, за своей подписью.

## Шаг 5 — итоговый отчёт

Собери **`05-final-report.md`** на основе файлов 01–04 (не пересобирай
данные заново, ссылайся на конкретные файлы/строки). Обязательные разделы:

```markdown
# QA-прогон перед релизом — <дата/время>

## Что прогнали
(изменённые файлы из 01, npm test из 03 — команда и версия)

## Что упало
(список failed-тестов из 03, с указанием — известный ли это дефект и с
каких пор, или новая регрессия)

## Что нового
(тесты/находки, которых не было в предыдущем прогоне qa-runs/*, если он
существует; новые пункты qa-spec.md, впервые затронутые правкой)

## Что осталось не покрыто
(из 02 — пункты spec без теста; из 04 — маскировки/пробелы, найденные
независимым агентом, даже если ты с ними не согласна — не вычёркивай)

## Честно: что не получилось или не успели проверить
Обязательный раздел, даже если пустой — тогда так и написать
«ничего не пропущено в этом прогоне», не удалять раздел.
```

Если шаг 4 по какой-то причине не удалось выполнить (агент не ответил,
инструмент недоступен) — не изображай, что независимая проверка прошла:
явно напиши в разделе «что не получилось», что шаг 4 пропущен, и почему.
Итоговый отчёт без реально пройденного шага 4 — неполный прогон, это нужно
показать пользователю, а не скрыть.

## В конце

Покажи пользователю путь `RUN_DIR` и краткую выжимку из
`05-final-report.md` (не весь файл целиком) в чате. Не коммить `qa-runs/`
без явной просьбы — по умолчанию это локальные регенерируемые артефакты,
как `test-results/`.
